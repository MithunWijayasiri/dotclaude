Documentation

Claude Code reads four kinds of file. This repo holds mine.

Claude Code loads its instructions from plain markdown in your home folder: output styles, skills, and a global CLAUDE.md. Nothing here is a plugin or a program. Every file is text you can read in a minute and edit with any editor.

I keep the folder in git so it survives a machine rebuild, and so anyone can lift a single file out of it. Output styles and CLAUDE.md are published. Skills land here as each one is generalised — a file that only makes sense inside one codebase is worth nobody else's time.

Read this page like a manual, not a pitch. Each section says what a file type does, where it goes, and what changes once Claude Code picks it up.

Reference

The three parts

They differ in scope and in when Claude Code loads them. That is the whole distinction — pick by the question "when should this apply?"

  • output-styles/Published

    One file replaces Claude Code's built-in guidance on how to answer. It loads into the system prompt when a session starts, so it shapes every reply until you switch. Two are here.

  • CLAUDE.mdPublished

    The standing instruction file. It loads in every session, in every project, so it stays short: engineering defaults, comment style, and which commands need approval first.

  • skills/Planned

    A repeatable job packaged as ~/.claude/skills/<name>/SKILL.md — a review checklist, a debugging procedure, a release sequence. Claude Code loads a skill on demand, when the task matches its description or you call it by name.

The skills/ folder holds a placeholder note for now. A hooks and settings.json reference is under consideration.

Published

Output styles

An output style is a markdown file with two frontmatter fields — name and description — and a body of writing rules. The body replaces Claude Code's default response guidance wholesale, so a style can change sentence length, banned words, and the shape of a result report.

The clearest way to see it: ask one question three times. The facts below are identical in all three answers. Only the shape moves.

claude style: ASD-STE100

> why does GET /api/users return 404?

The router sits on a different path. One file needs a change.

- Verified: server.js mounts the router at /api/user. The
  request asked for /api/users. The plural broke the match.
- Updated: None yet.
- Next: Confirm which spelling you want, then I will change
  the mount in server.js.
The request fails because the server registers a different path.

In server.js the router is mounted at /api/user, with no s at
the end. The request asks for /api/users. Express compares the
two, finds no match, and answers with 404.

Tell me which spelling you want to keep. Then I will change either
the mount or the request, so both sides use one path.
Thanks for flagging this — I've taken a look and I believe I've
identified the underlying cause of what you're seeing here. It appears
that the Express router responsible for user resources is currently
being mounted at /api/user inside server.js; however, the
request being issued is targeting /api/users, with a trailing
plural on the resource segment.

Because Express performs exact prefix matching on a mounted router,
the incoming request never reaches the handler you would expect, and
the default 404 handler ends up responding instead. This is a fairly
common class of issue in projects where route paths are not
centralised, since the mount path and the calling path are declared
in two entirely separate places.

There are a few different approaches we could potentially take here.
We could simply update the mount path to the plural form, though that
would leave the same duplication in place. Alternatively, we could
introduce a shared route constant that both sides import, which would
be considerably more robust going forward. Let me know which
direction you'd prefer and I'd be happy to help you implement it!

Primary

ASD-STE100

Structured output following ASD-STE100 English standards that any reader can understand. Named after the controlled English for aircraft maintenance manuals — where a technician must not read a procedure two ways.

  • One term per meaning, held for the whole answer
  • Max 20 words per sentence, simple tenses, no -ing forms
  • Active voice, imperative instructions
  • Six preferred words: utilize → use, initiate → start
  • Result first, then Verified: Updated: Skipped: Remaining: Next:
  • Each label once; two or more items nest under it

Lighter

Always Friday

Simple, clear output that's easy to read — like Friday afternoon. Short sentences and everyday words, with no label protocol and no grammar limits. It reads as ordinary prose. Reach for it when you explain the work to a person instead of filing a result — a handover note, or a summary for someone who missed the session.

  • Answer first, detail after
  • Every fact, name, number, and path kept
  • One idea per sentence, everyday words
  • Code, commands, and log output left untouched
  • No labels, no preamble, no sign-off

Procedure

Install

Get the files, then copy the parts you want into ~/.claude/. There is nothing to build. Create a folder if it is not there yet.

No git? Download the ZIP and unzip it. It unpacks to dotclaude-main/ rather than dotclaude/, so adjust the paths below by that one word.

Use a .claude/ folder inside a repo instead of ~/.claude/ to scope any of this to that one project. Copying CLAUDE.md replaces whatever sits at the target, so read your own first.

Turn on an output style

Copying the file does not select it. Type /config in a session and pick one under Output style. Claude Code saves that choice per project, in .claude/settings.local.json.

The value is the name: field from the file's frontmatter, not the filename. A style is part of the system prompt, so it takes effect after /clear or in your next session.
